## Findings

### ERPNext / Frappe

1. **Default "Required By" date is forward from today, not backward from need.** When a Material Request is made from a Production Plan, each row's date is `schedule_date = item.schedule_date or add_days(nowdate(), cint(item_doc.lead_time_days))`. So if the user leaves the plan row's "Required By" (`schedule_date`) blank, the date is today plus the item's lead time. There is no backward offset from the finished-good need date, and the Sales Order delivery date is not used for this date. | `services/material_request.py`, line 109 (fn `_add_item_to_material_request`) | Frappe / ERPNext GitHub | develop branch, last commit to file 2026-10-17 (sha 8a6725f) | accessed 2026-11-02 | https://raw.githubusercontent.com/frappe/erpnext/develop/erpnext/manufacturing/doctype/production_plan/services/material_request.py | high | erp-behaviour | primary (source code)

2. **There is no past-date check. A required date in the past is not handled.** Neither `material_request.py` nor `production_plan.py` compares `schedule_date` to today. The default (today + lead time) can never fall in the past. A date the user typed in, or a sub-assembly date, is passed through unchanged. The code has no "past due" or compression logic. | same files; `validate()` calls only `validate_data`, `validate_sales_orders`, `validate_material_request_type`, `validate_raw_material_group_warehouse` | Frappe GitHub | develop, 2026-10 | accessed 2026-11-02 | same URL plus https://raw.githubusercontent.com/frappe/erpnext/develop/erpnext/manufacturing/doctype/production_plan/production_plan.py | medium-high (absence claim, from reading two files plus a grep) | erp-behaviour | primary

3. **Sub-assemblies inherit the parent's start date with no lead-time offset per level.** In `set_sub_assembly_items_based_on_level` the line is `data.schedule_date = row.planned_start_date`, where `row` is the finished-good Production Plan Item. `sub_assembly_queries.py` has no date or lead-time logic. Multi-level planning is therefore not time-phased: every level gets the finished good's planned start date. | `services/sub_assembly.py`, line 101; `services/sub_assembly_queries.py` | Frappe GitHub | develop, 2026-10 | accessed 2026-11-02 | https://raw.githubusercontent.com/frappe/erpnext/develop/erpnext/manufacturing/doctype/production_plan/services/sub_assembly.py | high | erp-behaviour | primary

4. **BOM level is a recursion depth, not a low-level code.** `get_sub_assembly_items(..., indent=0)` walks `get_bom_children(parent=bom_no)` recursively with `indent + 1`. It sets `"bom_level": indent`. When the same sub-assembly occurs more than once, the merged row keeps `existing_row.bom_level = max(existing_row.bom_level, row.bom_level)`, which resembles a low-level code but is computed only within one plan. Nothing sorts by `bom_level` and there is no level-by-level netting pass: output is in insertion order. Phantom items are recursed into but not added as rows. | `services/sub_assembly_queries.py`, `services/sub_assembly.py` (`_merge_subassembly_row`) | Frappe GitHub | develop, 2026-10 | accessed 2026-11-02 | https://raw.githubusercontent.com/frappe/erpnext/develop/erpnext/manufacturing/doctype/production_plan/services/sub_assembly_queries.py | medium-high (summarizer read of this file; key lines quoted) | erp-behaviour | primary

5. **Netting is single-period and optional, against the bin's projected qty.** Raw-material requirement: `projected_qty = max(0, flt(bin_dict.get("projected_qty"))) if ignore_existing_ordered_qty else 0`, then `required_qty = max(0, qty - (available_qty - safety_stock))`. Despite its fieldname, `ignore_existing_ordered_qty` carries the label **"Consider Projected Qty in Calculation (RM)"**. With it off, no stock or open orders are netted and the gross BOM quantity is requested. Safety stock is added only when "Include Safety Stock in Required Qty Calculation" is on. Sub-assemblies net only with "Consider Projected Qty in Calculation" (`skip_available_sub_assembly_item`), by consuming `available_qty`/`projected_qty` from the bin. All netting uses a single projected-qty number with no time buckets. | `material_request.py` lines 678-684; `production_plan.json` field labels | Frappe GitHub | develop, 2026-10 | accessed 2026-11-02 | https://raw.githubusercontent.com/frappe/erpnext/develop/erpnext/manufacturing/doctype/production_plan/production_plan.json | high | erp-behaviour | primary

6. **There are no exception or action messages, only informational notes.** The only planning-type message is `"As there are sufficient raw materials, Material Request is not required for Warehouse {0}."` plus `"If you still want to proceed, please enable {0}."`. The sub-assembly path has a matching one ("Work Order is not required for Warehouse {0}"). There are no reschedule-in/out, cancel or past-due messages, and existing open POs/MRs are never re-dated. | `material_request.py` `_warn_no_mr_items`; `sub_assembly.py` `_warn_sufficient_sub_assembly` | Frappe GitHub | develop, 2026-10 | accessed 2026-11-02 | (URLs above) | high | erp-behaviour | primary

7. **There is no planning horizon. The From/To dates only filter which Sales Orders are pulled in.** In `planning_queries.py`: `"from_date": so.transaction_date >= plan.from_date`, `"to_date": so.transaction_date <= plan.to_date`, `"from_delivery_date": so_item.delivery_date >= plan.from_delivery_date`, and the matching `to_delivery_date`. These are optional filters on the source documents, not a time-phased horizon. | `services/planning_queries.py` lines 163-166 | Frappe GitHub | develop, 2026-10 | accessed 2026-11-02 | https://raw.githubusercontent.com/frappe/erpnext/develop/erpnext/manufacturing/doctype/production_plan/services/planning_queries.py | high | erp-behaviour | primary

8. **The user manual confirms single-bucket netting and is silent on lead time, dates and horizon.** "Required Qty = BOM Required Qty – Projected Qty". For sub-assemblies, "the system will consider the Projected Qty which is available in the bin". It also says "You don't need to use all these filters if you have only a few Sales Orders in a particular time frame." The page does not cover lead time, required-by dates, a horizon or exception messages. | Production Plan | Frappe (docs.frappe.io; docs.erpnext.com redirects here) | page updated 2026-02-27 | accessed 2026-11-02 | https://docs.frappe.io/erpnext/user/manual/en/production-plan | high | erp-behaviour | primary

9. **Lead time on the material request side only picks a supplier.** A newer "Item Lead Time" doctype has an "Item Lead Time Supplier" child table. `_get_default_lead_time_suppliers` uses it only to fill in the default `supplier` on MR rows. The date still comes from `item_doc.lead_time_days`. | `material_request.py` lines 586-610 | Frappe GitHub | develop, 2026-10 | accessed 2026-11-02 | (URL in 1) | medium (exists on develop; not checked in v15 or v16 release branches) | erp-behaviour | primary

## Disagreements

- **ERPNext fieldname vs label.** The field `ignore_existing_ordered_qty` is labelled "Consider Projected Qty in Calculation (RM)", and the code nets projected qty only when it is set, which is the opposite of what the fieldname says. Older docs or blogs that describe "Ignore Existing Projected Quantity" have the logic inverted relative to current develop. Check the v15/v16 release branches before citing.
- **ERPNext manual vs code.** The manual states "Required Qty = BOM Required Qty – Projected Qty" without saying this depends on a checkbox. In the code, netting is off unless the "Consider Projected Qty" flag is set.
- **Oracle Acceptable Early Days scope.** The official Release 11 text says it damps reschedule-*out* only, and reschedule-*in* is always issued. A MOSC community post (snippet only, user report) claims it limits "Orders to be rescheduled in". Prefer the official text. The Cloud version may behave differently; this is unverified.
- **Oracle "Past due" definition varies by version.** Release 11 says "orders that are past due" (no date anchor stated on the page). Cloud 26B (snippet) says due date "before the plan horizon start date".
- **SAP message texts.** AFS 6.0 wording ("Give priority to the procedure", "Timely planning of the procedure") differs from the usual ECC texts ("Bring process forward", "Plan process according to schedule"). The numbers agree; this looks like a translation artifact.
