# A3 digest: How ERP systems present planned orders whose release falls in the past (ERP-documentation angle)

Researcher run A-r1-2, accessed 2026-11-02. The hypothesis under test: the app puts the release in week 1, keeps the receipt in need week t, and shows the lateness only as an exception message.

## Findings

1. **SAP S/4HANA: the system switches to forward scheduling from today.**
   - Claim: when backward scheduling gives a start date in the past, the system automatically forward-schedules from today. This is option (b): the start moves to today, so the finish/receipt moves to today + lead time. Exact quotes: "If an order start date is calculated during backward scheduling with a start date in the past, the system automatically switches to forward scheduling, using the current date as the order start date." A second sentence makes the switch conditional: "it is possible to execute a forward scheduling automatically, if allowed."
   - Source: "Understanding MRP in SAP S/4HANA" (course *Exploring Production Planning in SAP S/4HANA*), SAP Learning. Version: course S42220_26 per the image paths; no product release is stated.
   - URL: https://learning.sap.com/courses/exploring-production-planning-in-sap-s-4hana/understanding-mrp-in-sap-s-4hana
   - Confidence: high that this is SAP's described behaviour. The two sentences on one page are inconsistent: one says "automatically", the other says "if allowed".
   - Class: erp-behaviour. Primary.

2. **SAP: the behaviour is controlled in Customizing, and today scheduling raises exception message 30.**
   - Claim: whether past start dates are allowed is set per MRP group, in transaction OPPR under the "Start in past" button. If past dates are not allowed, MRP forward-schedules from today to calculate a new delivery date, and the result is flagged with exception message 30, meaning today scheduling was carried out. It follows that if past dates *are* allowed within the tolerance, the order keeps its requirement date and its start date stays in the past. That is option (a), plus a start-in-past exception.
   - Source: "The causes of exception message 30 in transactions MD04 and MD05", SAP Support Content (MRP), SAP. No version date given.
   - URL: https://help.sap.com/docs/SUPPORT_CONTENT/mrp/3138697939.html
   - Confidence: medium. The page is rendered in JavaScript and WebFetch returned only its title. The content above comes from the search-engine summary of the page, not from a full read.
   - Class: erp-behaviour. Primary page, but only seen through the snippet.

3. **SAP: the exception-message texts for past dates.**
   - Claim: SAP's own exception monitor guide gives these meanings:
     - Message 07: "basic finish date in past" for PP orders, and "delivery date in past" for purchase orders.
     - Message 30: "dispatch process on time" for planned orders.
     - Message 10: "bring process forward".
     - Message 15: "postpone process".
     - Message 20: "cancel process".
   - Source: "MRP Exception Monitor" (/SAPLOM/ERM add-on guide, PUBLIC), SAP. Version 2024.1, dated 2024-11-06. It has a section on S/4HANA-exclusive functions.
   - URL: https://help.sap.com/doc/80c6ad471d2d42598c766e3ef5c1fac4/2024.1/en-US/ERM-EN-PUBLIC.pdf
   - Confidence: high for the message texts listed.
   - Class: definition. Primary.

4. **SAP: messages 05 and 06 (secondhand only).**
   - Claim: message 05 = "opening date in the past" and message 06 = "start date in the past". Practitioners describe both as standard messages, not something you configure. One poster says 05 can be reproduced by editing the opening date in MD12. For 06, the advice is that the MRP controller must act, usually by rescheduling to today.
   - Source: SAP Community Q&A threads, answers.sap.com (2012, 2017).
   - URLs:
     - https://answers.sap.com/questions/9431874/regarding-exception-message.html
     - https://answers.sap.com/questions/276992/planned-order-is-not-showing-exception-message-05.html
   - Confidence: low to medium. These are community posts, not official documentation.
   - Class: definition. Secondhand.

5. **Microsoft Dynamics 365 Supply Chain Management: "Delays" (formerly "futures messages").**
   - Claim: a past order date leads to forward planning from today, which is option (b). The transaction gets a delayed date and a count of delay days. Exact quotes:
     - "If master planning calculates an order date that precedes the current date, the order can't be fulfilled on time. Therefore, the order is delayed. In this case, master planning forward-plans the order from the current date and includes lead times."
     - "The order then receives a delayed date. A delayed date is a realistic due date ... Master planning also calculates the number of delay days."
     - Terminology: "In earlier versions, calculated delays were known as *futures messages*, the delayed date was known as the *futures date*."
     - Delay calculation can be switched off ("you might choose not to calculate delays"). It is configured per coverage group.
     - The planned order keeps a **Desired date**, which is "the base date for delays". So the original requirement date is kept next to the delayed date.
     - Known limitation: with multiple BOM levels, "only the items directly above the item ... causing the delay, will be updated with a delay".
   - Source: "Delays – Supply Chain Management", Microsoft Learn, Microsoft. ms.date 2025-08-22, updated 2026-09-01.
   - URL: https://learn.microsoft.com/en-us/dynamics365/supply-chain/master-planning/delays
   - Confidence: high.
   - Class: erp-behaviour. Primary.

6. **D365: action messages are a separate mechanism.**
   - Claim: "An action message is a system-generated suggestion to change an existing planned, approved, or firmed order" (advance, postpone and so on). This is distinct from delays.
   - Source: "Action messages – Supply Chain Management", Microsoft Learn. The quote is from the search snippet; the page itself was not fetched.
   - URL: https://learn.microsoft.com/en-us/dynamics365/supply-chain/master-planning/action-messages
   - Confidence: medium.
   - Class: definition. Primary, but seen through the snippet.

7. **Odoo 18: lead-time dates and late orders.**
   - Claim: Odoo dates purchases forward. The Order Deadline is the "Last calendar day to confirm the RFQ and convert it to a PO". Expected Arrival is "Calculated by *Order Deadline* + *Vendor Lead Time*". In the worked example, the order deadline = today + Days to Purchase.
   - A PO "is marked late if the *Expected Arrival* date has passed". It then shows in a "Late" box on the Purchase dashboard.
   - Sales: "Odoo issues a warning message if the set delivery date is earlier than the expected date".
   - Odoo has no MRP-style exception code. Lateness shows up as a dashboard status or a warning.
   - Source: "Lead times", Odoo documentation, Odoo S.A. Version 18.0. Only the first 100k of 107k characters were read.
   - URL: https://www.odoo.com/documentation/18.0/applications/inventory_and_mrp/inventory/warehouses_storage/replenishment/lead_times.html
   - Confidence: medium. The page does not say explicitly what happens when the computed deadline falls before today.
   - Class: erp-behaviour. Primary.

8. **ERPNext/Frappe: no documented past-date rule found.**
   - Claim: the Production Plan Scheduler applies the rule that production cannot start before raw material arrives. Procurement time comes from Item Lead Time or Supplier Lead Time (Purchase Time + Buffer Time). A Material Request carries an editable "Required By" date.
   - Source: "Production Plan Schedule" and "Material Request", Frappe/ERPNext docs (docs.frappe.io). Version not stated. Seen through search snippets only.
   - URL: https://docs.frappe.io/erpnext/production-plan-schedule
   - Confidence: low.
   - Class: erp-behaviour. Primary, but seen through the snippet.

## Disagreements between sources

- **Within the SAP Learning page:** one sentence says the switch to forward scheduling happens "automatically". The next says it happens only "if allowed". The SAP support note (seen as a snippet) settles this: the "Start in past" setting on the MRP group (OPPR) decides it.
  - Within the allowed tolerance, SAP keeps the receipt on the requirement date and leaves the start in the past. This is (a), with a start-in-past exception (05/06, secondhand).
  - Beyond the tolerance, SAP forward-schedules from today and flags exception 30. This is (b).
- **Across vendors:**
  - Dynamics 365 defaults to (b): it forward-plans from today and shows a delayed date plus delay days. It keeps the "Desired date" as a reference, and delay calculation can be switched off per coverage group.
  - Odoo dates forward from today by construction and flags late POs on its dashboard.
- **Against the app's hypothesis:** none of the systems found does what the app does. The app moves the release to week 1 *and* keeps the receipt in week t, so its release-to-receipt span is shorter than the lead time. SAP's option (a) keeps the start in the past rather than clamping it to today. Option (b), in SAP and D365, moves the receipt later.
- **Messages 05/06:** the community threads disagree on whether OPPQ (plant level) or OPPR (MRP group) holds the past-start setting.
