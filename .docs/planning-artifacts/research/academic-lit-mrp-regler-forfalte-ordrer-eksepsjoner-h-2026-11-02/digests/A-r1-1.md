## Synthesis against the hypothesis (tentative, not textbook-verified)

- **A1, release placement:** Every source found agrees the release is *flagged* (past-due / release-overdue / expedite message). Two weak sources (1, 3) suggest it is placed in, or lumped into, period 1. Oracle (5) shows past-due items in the first bucket. A separate "past due" column is common in textbook MRP grids from memory, but I found **no retrieved evidence** for it this run (unverified belief).
- **A2, receipt placement:** The hypothesis (receipt stays in need week t, PAB assumes on-time cover, lateness shows only as an exception) fits the naive "lump into period 1" algorithm (3) and the grid example (2). ERP sources (6, 7) instead show a pattern where receipts are not planned earlier than today (+ lead time), with lateness made explicit as "projected late" days. Source 8 treats lead-time compression as a non-standard proposal. **There is no evidence that compression is "the textbook norm".** In the sources found, it is implicit in the naive algorithm and is flagged as an infeasibility.

## Disagreements between sources

- **Receipt timing:** The naive/textbook-style grid keeps the receipt at the need date (2, 3). Some ERPs keep the receipt no earlier than today + lead time and report it as late (6 Move In / Rcpt Projected Late; 7 "due today" plus a past-due order-by date). Oracle (5) moves past-due items *to day 1* rather than leaving them late.
- **Status of compression:** Source 3 (reported) treats lumping into period 1 as the standard algorithm's behaviour. Source 8 presents emergent (compressed) lead time as a new method, which implies it is not standard.
